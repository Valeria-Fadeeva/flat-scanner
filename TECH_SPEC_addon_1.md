# 1. TECH_SPEC_addon_1.md: Расширенные инженерные требования (Инфраструктурный слой)

## 1.1. Отказоустойчивость ядра обработки контуров (OpenCV Safe-Guards)
При детекции страниц алгоритм find_contours и последующая аппроксимация approx_poly_dp подвержены геометрическим аномалиям из-за бликов или замятия страниц.
*   Запрет на панику: Архитектурно запрещено передавать невалидный массив точек в функцию get_perspective_transform. Любое исключение C++ (OpenCV Exception) должно быть перехвачено на стороне Rust-биндингов.
*   Геометрическая валидация: Перед расчётом матрицы гомографии модуль ОБЯЗАН проверить следующие условия:
    1. Массив аппроксимированного контура должен содержать строго 4 точки.
    2. Площадь полученного четырёхугольника (contour_area) должна составлять не менее 15% от общей площади сырого кадра (защита от ложных микро-контуров).
    3. Контур должен быть выпуклым (is_contour_convex).
*   Обработка сбоя: Если условия нарушены, функция детекции не имеет права вызывать панику или возвращать unwrap(). Модуль обязан вернуть ошибку в безопасном Rust-формате: Result::Err(DigitizationError::InvalidPageGeometry). Страница в базе данных SQLite должна получить статус FAILED с записью лога ошибки в поле error_message.

## 1.2. Асинхронная изоляция блокирующего ввода-вывода (SANE FFI Guard)
Си-библиотека sane-backends выполняет чтение данных со сканера через синхронный блокирующий вызов sane_read.
*   Изоляция потоков (Thread Starvation Prevention): Категорически запрещено вызывать функции SANE FFI напрямую внутри стандартных асинхронных функций Axum-обработчиков. Это приводит к блокировке потоков планировщика Tokio (Tokio worker threads) и зависанию веб-сервера.
*   Паттерн реализации: Все операции инициализации сканера, опроса устройств и побайтового чтения пикселей из Си-буфера должны быть принудительно обёрнуты в макрос tokio::task::spawn_blocking.
*   Управление памятью: Буферы данных, выделяемые SANE на стороне Си, должны немедленно копироваться в безопасные векторы Rust (Vec<u8>) с явным вызовом деструкторов Си-структур (RAII паттерн через реализацию трейта Drop), чтобы исключить утечки памяти при многочасовом сканировании.

## 1.3. Управление конкурентностью SQLite WAL и упорядочивание задач
Несмотря на включённый режим PRAGMA journal_mode = WAL, интенсивная параллельная работа (одновременный захват изображения со сканера, Dewarping на GPU через OpenCV и запись OCR-текста) может вызвать ошибку database is locked.
*   Архитектура очереди (FIFO Task Queue): В бэкенде Axum должна быть реализована строгая однопоточная очередь задач на базе асинхронных каналов tokio::sync::mpsc. 
*   Единственный писатель (Single Writer): Монопольное право на выполнение транзакций записи, обновления статусов страниц (update_page_status) и изменения метаданных книг имеет строго один выделенный фоновый воркер, читающий задачи из канала. Чтение данных из базы (get_book_progress, get_pending_pages) может выполняться параллельно из Axum-потоков.
*   Транзакции: Любое комплексное обновление (например, перевод страницы из статуса RAW в DEWARPED с сохранением новых путей к файлам) должно выполняться внутри атомарной транзакции conn.transaction()?. В случае сбоя файловой системы или нехватки места, транзакция должна выполнить автоматический rollback.
